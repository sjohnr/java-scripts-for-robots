# javaw (Java)

`javaw` generates a relocatable POSIX `sh` launcher for a Java program. It is never in the launch path.

| File | Purpose |
|---|---|
| `Javaw.java` | the tool, one source file with no dependencies |
| `javaw` | its launcher, generated by the tool itself (`java Javaw.java -o javaw Javaw.java`) |
| `JavawTest.java` | tests: kebab-case, quoting, CLI errors, and running real wrappers |
| `examples/Hello.java` | example program: prints its arguments and `app.version` |

## Run it

```sh
./javaw --help
./javaw examples/Hello.java                    # writes ./run-hello
./run-hello a b                                # hello a,b version=1
./javaw --jar tool.jar --min-java 21 --jvm-opts "-Xmx1g" -o bin/
./javaw A.java B.java -o bin/                  # one wrapper per input
```

`--jvm-opts` is split at spaces and each option is quoted on its own. `--classpath` and `--java-home` are written into the wrapper exactly as given.

## Test

```sh
java JavawTest.java     # run from this directory; needs JDK 22+ (multi-file source launch)
```

The tests generate wrappers in a temporary directory and run them:
- from another directory
- through a relative symlink and through a chain of two symlinks
- through `PATH`
- after the directory is moved
- with `JAVA_TOOL_OPTIONS=-Dapp.version=2`
- with `CDPATH` exported while the wrapper is invoked as `app/run-hello` and `CDPATH` contains a decoy `app` directory
- through a path starting with `-`

They also check `--min-java` against the real JVM and against a fake `--java-home` JVM that reports `1.8.0_392`, `28-ea`, an unparseable version, or no JVM at all.
